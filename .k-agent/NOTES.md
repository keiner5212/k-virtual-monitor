# Workspace notes

- Tauri command responses are camelCase: the response structs in `apps/desktop/src-tauri/src/lib.rs` carry `#[serde(rename_all = "camelCase")]`. `ServerConfig` stays snake_case because it is also the TOML file format.
- `pnpm format:check` fails on the baseline: there is no prettier config here, so prettier defaults (2 spaces, 80 columns) disagree with the code (4 spaces, 100 columns). Do not run `pnpm format`; match the surrounding style instead.
- The device store file `~/.local/state/kvm/devices.json` is the source of truth. The server reloads it at handshake time, so a pairing code created by `kvm-desktop --pair` is accepted by a server that is already running.
- Never push: the user pushes. The git remote is https without credentials, so a push would need the SSH alias `git@github-com-personal:keiner5212/k-virtual-monitor.git`.
- Keep the lockfile in the same commit as the `package.json` that changes it, so every commit installs with `--locked`.
- All Flatpak apps are pinned to the Intel iGPU by `flatpak override --user`: `VK_DRIVER_FILES=/usr/share/vulkan/icd.d/intel_icd.x86_64.json`, `__EGL_VENDOR_LIBRARY_FILENAMES=.../50_mesa.json`, `MESA_LOADER_DRIVER_OVERRIDE=iris`. Without it they pick the RTX 3050 through the NVIDIA Vulkan ICD. Override only affects new processes, so restart the app after changing it.
- Expo SDK 58 consumes expo modules as prebuilt Android artifacts, so a patched native source is ignored. `apps/mobile/package.json` sets `expo.autolinking.buildFromSource: ["expo-camera"]` so the patch in `patches/` reaches the APK. Without it the phone camera keeps the stock code.
- The desktop capture finds the virtual screen by name, never by the `kscreen-doctor` output id: the ids shift when the layout changes, and the built-in screen of the user must never be resized.
- The portal permission is in `~/.local/state/kvm/portal.json` (restore token, owner only). With it the consent dialog only appears the first time.
- The protocol interop test always uses the synthetic source (it sets `KVM_SYNTHETIC=1`), so it is the same everywhere. The check of the session of the phone (`apps/mobile/test/session.test.ts`) runs the client of the phone against the real server the same way, and `KVM_SYNTHETIC_QUIET=1` makes the pattern behave like the compositor, which paints only when the screen changes.
- The screencast of the portal is damage driven: KWin paints the virtual output only when something changes (about 10 ms from the change to the picture) and neither the portal nor KWin has a frame rate knob. The encoder repeats the last picture, so the stream keeps its rate. The stream of the portal has a variable framerate (`0/1`), so `videorate` has to stay in the `drop-only` mode: without it, videorate tries to catch up with the gap and the capture stalls for minutes.
- The picture path has two rules that are easy to break: the GLib timer of the python child of the encoder must return True (PyGObject takes the timer away when it returns None, and the stream falls back to the rate of the compositor), and the decoder of the phone needs every picture in order (a picture that depends on another one cannot be drawn when that other one was lost, so the decoder takes the pictures from the feed and not from the state of the interface).
- The frames of the portal arrive in dma-bufs. Their size is in the chunk, not in the data (the size of the data is zero), so mapping them with `data.maxsize` throws every picture away. GStreamer, which the old python server used, gets this right.
- `kscreen_osd_service` crashes with SIGSEGV when the virtual output appears or disappears. It is KDE bug 498878 (a config with an unknown output), not our code. The community workaround is masking `plasma-kscreen-osd.service`.
- The phone app builds as a dev client with `expo-dev-client` and the `development` EAS profile. The plugin is applied automatically by `@expo/prebuild-config` (it is in `legacyExpoPlugins`), so it is not listed in `app.json`. The native projects are generated by `expo prebuild`, never committed.
- The desktop owns the size of the stream and the phone owns its id. The list of sizes lives in `packages/protocol/ts/src/resolutions.ts` so both apps read the same one.
- The QR scanner has two paths: the scanner of the system (`CameraView.launchScanner`, Google code scanner) and the analyzer of the camera in the app (`onBarcodeScanned`, ML Kit). The system one is the path Expo uses and tests on Android; the in-app one is legacy and has no Android end to end test. The system one needs the release build NOT to be shrunk: `expo-build-properties` with `enableProguardInReleaseBuilds: false`, the app.json key alone does nothing in SDK 58. Expo Go reads QR codes on that phone, so the camera and the ML Kit are fine there: Expo Go is built with `assembleDebug`, so it is never shrunk: the difference from our release APK was the shrinking (expo/expo#52145).
- The Kotlin of the phone can be checked without the Android SDK: the compiler in `.tmp/kotlin` (the official zip, never installed in the system) with the stubs in `.tmp/kotlin-stubs` compiles the real file and can run its logic over a real stream. It caught a `wait()` on an `Any` that broke the build of the app.
- The last version that sent the pictures well was `ce70085` (the python server). Its snapshot is in `.tmp/ref-ce70085` with a README; `.tmp` is not in git, so take the snapshot again when it is gone.
- Standing project rules live in `AGENTS.md`: builds and temp output go to `./.tmp` (never `/tmp`), commit recurrently but never push, keep CI green.
